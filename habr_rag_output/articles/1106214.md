# Как я заставил Windows Server 2003 выйти в современный интернет (и что из этого вышло)

Привет, Хабр! Недавно я поднимал в VirtualBox старую Windows Server 2003 R2. Кто-то скажет: «Зачем?». А мне было интересно, как поведет себя система, которая перестала получать обновления много лет назад, если её попробовать «подружить» с современной сетью.

Эпоха Windows Server 2003 и Windows XP — это время, когда интернет был другим. Тогда не было повсеместного HTTPS, сайты весили по 50 килобайт, а основным браузером был Internet Explorer 6. С тех пор веб-стандарты ушли далеко вперед, а протоколы безопасности (TLS) были переписаны с нуля. И если старую систему можно запустить в виртуалке ради ностальгии, то выйти с её помощью в современный интернет — это настоящий вызов.

Главная проблема, с которой я столкнулся — это отсутствие современных протоколов безопасности. Internet Explorer 8 (максимальная версия для Server 2003) физически не может открыть ни один современный сайт, так как он не понимает новые шифры.

#### Теория: Почему IE8 ломается на современных сайтах

Чтобы понять суть проблемы, нужно заглянуть в то, как работает защищенное соединение. Современный веб использует протокол TLS, и сегодня актуальной версией является TLS 1.3 (и TLS 1.2 с большими оговорками).

Процесс установки соединения выглядит так: клиент и сервер обмениваются приветствиями, договариваются о поддерживаемых версиях шифрования и обмениваются ключами. Проблема в том, что IE8 поддерживает только устаревшие и небезопасные версии: SSL 3.0, TLS 1.0 и иногда TLS 1.1. Современные серверы (например, Cloudflare или крупные хостинги) уже давно отключили поддержку этих старых протоколов из-за уязвимостей (таких как POODLE или BEAST). Когда IE8 пытается постучаться на современный сайт, сервер просто обрывает соединение, так как не может договориться с ним о безопасном шифре.

Решать это переустановкой системы или поиском старых патчей было неинтересно (к тому же, это небезопасно). Я решил пойти путем написания промежуточного звена — «моста» между древним гостем и современным хостом.

#### Архитектура решения и настройка изоляции

Я отбросил несколько альтернатив. Например, установку старых версий браузеров с ручным включением TLS 1.2 (это ломает систему и оставляет дыры в безопасности), или поднятие локального reverse-proxy на Nginx (слишком громоздко для одной виртуалки).

Мой выбор — написать собственный HTTP-прокси на Python. Архитектура предельно простая:

1. На хосте (Windows 10 LTSC) запускается скрипт-прокси.
2. В настройках сети VirtualBox мы используем режим NAT.
3. Гостевая ОС настраивается на использование этого прокси.
4. Прокси принимает запрос от IE8, сам скачивает контент современными методами, и отдает его обратно в браузер.

В VirtualBox есть несколько режимов сети. Если использовать «Сетевой мост», виртуалка получит реальный IP-адрес от вашего роутера и станет видимой для всей локальной сети. Это плохо, потому что старая необновляемая система сразу же станет целью для сетевых червей.

Режим NAT создает изолированную подсеть. Виртуальная машина получает IP 10.0.2.15, а хост доступен ей по адресу 10.0.2.2. Это идеальный «мост»: гость видит хост, но извне эту связку никто не видит. Поэтому в нашем Python-скрипте мы жестко прописываем HOST = '10.0.2.2' и никогда не используем 0.0.0.0, чтобы случайно не открыть прокси для всего интернета.

#### Написание кода и работа с сокетами

Теперь переходим к коду. Нам понадобятся стандартные библиотеки socket, threading и urllib.request.

Сначала создаем функцию для обработки одного клиента. Она будет читать входящий запрос, парсить из него URL и отправлять его дальше. Важно подменить User-Agent на современный, иначе многие сайты просто отдадут ошибку 403 (Forbidden), поняв, что к ним стучится «древний» клиент.

Далее мы формируем правильные заголовки для ответа. IE8 очень капризен. Если мы не передадим Content-Type и Content-Length, браузер может просто обрезать ответ или не применить стили. Также важно помнить про метод CONNECT: если IE8 пытается использовать HTTPS через туннель, мы вежливо отказываем, так как для наших целей достаточно обычного HTTP.

```
import socket
import threading
import urllib.request
HOST = '10.0.2.2'
PORT = 8080
def handle_client(client_socket):
    try:
        request = client_socket.recv(4096)
        if not request:
            return
        first_line = request.split(b'\r\n')[0].decode('utf-8', errors='ignore')
        parts = first_line.split(' ')
        if len(parts) < 2:
            return
        method, url = parts[0], parts[1]
        if method == 'CONNECT':
            client_socket.send(b"HTTP/1.1 501 Not Implemented\r\n\r\n")
            return
        if not url.startswith(('http://', 'https://')):
            url = 'http://' + url
        req = urllib.request.Request(url, headers={'User-Agent': 'Mozilla/5.0'})
        with urllib.request.urlopen(req, timeout=10) as response:
            content = response.read()
            content_type = response.headers.get('Content-Type', 'text/html')
        headers = (
            f"HTTP/1.1 200 OK\r\n"
            f"Content-Type: {content_type}\r\n"
            f"Content-Length: {len(content)}\r\n"
            f"Connection: close\r\n\r\n"
        )
        client_socket.send(headers.encode())
        client_socket.send(content)
    except Exception:
        try:
            client_socket.send(b"HTTP/1.1 500 Error\r\nContent-Length: 0\r\n\r\n")
        except Exception:
            pass
    finally:
        client_socket.close()
def start_proxy():
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((HOST, PORT))
    server.listen(20)
    try:
        while True:
            client_sock, addr = server.accept()
            threading.Thread(target=handle_client, args=(client_sock,), daemon=True).start()
    except KeyboardInterrupt:
        pass
    finally:
        server.close()
if __name__ == "__main__":
    start_proxy()
```

Почему мы используем threading.Thread для каждого соединения, а не обрабатываем запросы в цикле? Всё дело в том, как работает IE8. Когда браузер загружает страницу, он отправляет несколько параллельных запросов: сначала HTML, потом CSS, потом картинки. Если наш прокси будет обрабатывать их по очереди (синхронно), то пока он качает одну картинку, остальные запросы будут висеть в очереди. Браузер решит, что сервер «завис», и оборвёт соединение.

Многопоточность решает эту проблему. Каждый запрос от IE8 попадает в отдельный поток, который живёт своей жизнью. Пока один поток качает CSS, другой уже отдаёт HTML, а третий запрашивает картинку. Для старого браузера это выглядит так, будто сервер отвечает мгновенно.

Однако есть нюанс с библиотекой socket. В Python сокеты по умолчанию работают в блокирующем режиме. Когда мы вызываем client\_socket.recv(4096), программа замирает и ждёт, пока придут данные. Если клиент (IE8) замолчит и не закроет соединение, поток будет висеть вечно, пожирая память. Именно поэтому в коде есть конструкция try...finally, которая гарантированно закрывает сокет, даже если внутри произошла ошибка.

Также стоит упомянуть про urllib.request. Эта библиотека внутри использует http.client, который автоматически обрабатывает заголовки Connection: keep-alive и умеет работать с редиректами (кодами 301, 302). Нам не нужно писать это вручную — Python всё делает за нас.

#### Почему не Nginx и не старые браузеры?

Перед тем как писать свой прокси на Python, я рассматривал два альтернативных варианта.

**Вариант 1: Установка Nginx в качестве reverse-proxy.** Можно было бы поднять Nginx на хосте и настроить его как прокси для виртуалки. Но у этой идеи есть фатальный недостаток. Nginx — это современный сервер, который сам использует TLS 1.2/1.3 для исходящих соединений. Но когда он принимает запрос от IE8 (без шифрования, по HTTP), он просто перенаправляет его дальше. Проблема в том, что Nginx не умеет «переупаковывать» ответ под старые стандарты. Если сайт отдаёт современный CSS с grid или flexbox, IE8 его всё равно не поймёт. Nginx не занимается адаптацией контента. Наш Python-скрипт, хоть и не решает проблему с CSS, но даёт гибкость: мы можем в любой момент вырезать лишние скрипты или подменить заголовки.

**Вариант 2: Поиск старой версии Firefox или Chrome.** Можно было бы установить на Server 2003 старую версию Firefox (например, 3.6), которая ещё поддерживает TLS 1.0. Но здесь возникает другая проблема — безопасность. Старые браузеры содержат сотни известных уязвимостей (XSS, RCE), которые давно закрыты в новых версиях. Запускать такой браузер даже в виртуалке — это риск. Кроме того, современные сайты всё равно не будут работать, потому что они требуют поддержки ES6 (современного JavaScript), которой в Firefox 3.6 нет.

Таким образом, Python-прокси — это компромисс. Мы получаем гибкость и безопасность (скрипт изолирован), но платим за это необходимостью писать код вручную.

#### Результаты эксперимента и разбор багов

Когда код был готов, настало время испытаний. Я запустил прокси на хосте, открыл настройки IE8 в виртуальной машине и прописал адрес 10.0.2.2, порт 8080.

Первое, что я увидел — это была страница моего собственного сайта, написанная на HTML и CSS. И знаете что? Это сработало! Страница загрузилась. Конечно, она выглядела упрощенно, без современных JS-анимаций и сложного дизайна (так как IE8 не понимает ES6 и CSS3), но текст, базовые стили и ссылки отобразились абсолютно корректно.

Я решил проверить, как отреагируют другие сайты. И тут вылезли интересные особенности:

1. Яндекс и Google — ожидаемо отказались работать. Их современные фронтенды требуют полноценной поддержки JavaScript, которой в IE8 нет.
2. Сайты со сложной версткой — ломались. Если сайт использовал современные шрифты или сетки (Flexbox/Grid), IE8 их просто игнорировал.
3. А вот страницы с простым дизайном (например, текстовые блоги, документация) открывались отлично!

Вот таблица основных проблем, с которыми я столкнулся, и способов их решения:

| Проблема | Причина | Решение в коде |
| --- | --- | --- |
| «Кракозябры» вместо текста | IE8 не всегда угадывает кодировку UTF-8 | Добавление charset в заголовок Content-Type |
| Обрыв соединения на тяжелых сайтах | IE8 закрывает сокет, а Python продолжает ждать ответ | Установка таймаута в urlopen (timeout=10) |
| Отсутствие стилей CSS | IE8 не понимает новые MIME-типы | Проброс реального Content-Type от сервера |
| Сайт не открывается совсем | Редирект на HTTPS, который IE8 не тянет | Отказ на метод CONNECT с кодом 501 |

#### Вопросы безопасности и изоляции

Пока я тестировал этот мост, я вспомнил одну важную вещь. В самом начале я специально жестко привязал скрипт к адресу 10.0.2.2 и не использовал 0.0.0.0. И это было правильное решение.

Если запустить такой прокси в открытом виде (доступным из интернета), его моментально найдут боты. Открытый прокси — это дыра в безопасности, через которую злоумышленники могут рассылать спам, майнить криптовалюту или атаковать другие сайты, скрываясь за вашим IP-адресом. Я знаю это не понаслышке: мой провайдер блокировал IP-адреса из-за подобной активности, и это привело к попаданию в спам-базы (Spamhaus). Поэтому изоляция через VirtualBox NAT — это не просто удобно, это жизненно необходимо.

Также стоит помнить, что старые системы не получают обновлений безопасности. Если использовать такой прокси для работы с реальными данными, вы рискуете их скомпрометировать. Этот проект — исключительно для ретро-экспериментов и доступа к статической информации, не более того.

#### Выводы и планы на будущее

Этот эксперимент показал, что старые системы можно «оживить» для доступа к базовой информации, но для полноценной работы в современном вебе нужны либо специализированные текстовые браузеры (вроде Lynx), либо сложные прокси-серверы, вырезающие весь JS-код и адаптирующие CSS.

Было очень интересно посмотреть, как система 2003 года пытается «переварить» современный интернет. Она тормозит, ругается на сертификаты, не понимает новые теги, но все равно умудряется отрисовать текст и ссылки. В этом есть какая-то особая эстетика ретро-вычислений.

В планах попробовать проделать тот же трюк с Windows NT 4.0. Там ситуация ещё сложнее: в NT 4.0 вообще нет нормального TLS, а максимальный браузер (Internet Explorer 5) не поддерживает даже базовые шифры. Для неё придётся либо писать текстовый шлюз (который будет вырезать весь HTML и отдавать только текст), либо искать старые сборки Netscape Navigator. Это будет следующий уровень сложности в нашем ретро-эксперименте.

Если вы хотите повторить этот эксперимент, помните: используйте изолированный NAT, не открывайте порты наружу и не забывайте про таймауты в коде.
